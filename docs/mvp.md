
# MVP capability checklist and boundaries

Goal: build a “usable desktop player core + the thinnest possible UI” first, then expand step by step to mobile and advanced capabilities.

> Convention: this document discusses feature boundaries and interface placement only; it does not cover DRM/patent/store-term compliance details (see `docs/licensing.md`).

## 0. General principles

- **Desktop before mobile**: get the playback chain working on Windows/macOS/Linux first; on mobile, prefer a system framework or a separate backend.
- **Playback before media library**: first make “open → play → pause → drag → switch audio track/subtitle” stable, then do scanning/scraping/synchronization.
- **No DRM first**: Widevine/FairPlay and similar DRM are not part of the “plays anything” claim; when needed, go through a system player or a commercial solution.

## 1. Required for MVP (v0.1)

### 1.1 Media input

- Local files: `file://` or a direct path
- Basic URLs: `http(s)://` (whether segmented/adaptive is supported is left to the backend)
- Clear errors and state: the reason an open failed is visible

### 1.2 Playback control

- Play/pause/stop
- Seek (drag the progress bar)
- Playback speed (six steps: 0.5x/0.75x/1.0x/1.25x/1.5x/2.0x)
- Volume (0–100%) and mute

### 1.3 Tracks and subtitles

- Read `MediaInfo`: duration, whether it is seekable, the track list
- Select an audio track / a subtitle track
- Turn subtitles off
- Load external (sidecar) subtitles: `loadExternalSubtitle` attaches the `.srt`/`.vtt`/`.ass`/`.ssa`/`.ttml`/`.dfxp` files sitting next to the media as one selectable subtitle track (the rendering contract for ASS/SSA documents is in §6 batch 1b); the subtitle menu and the Subtitle Settings overlay list the candidates (see §6)

### 1.4 Events and metrics (observable)

- State-change events: playing/paused/stopped/ended/error
- Time events: position updates (for the UI progress bar)

### 1.5 Desktop UI (the thinnest layer)

- Floating control bar (OSC): bottom-centered, auto-hides after 2.5s without input; pinned while hovering / dragging / with an overlay open / paused
- Controls: a full-width seek bar (hover time tooltip, drag preview, commit on release) + transport controls, clock, volume, speed, audio/subtitle menus, information, fullscreen
- Keyboard and mouse: single click toggles the OSC, double click toggles fullscreen, vertical wheel = volume / horizontal (or Shift) wheel = seek, drag a file in to open it, recent items; empty main window (a GUI start with no source, BUGS.md #3): the `O` key / clicking the poster opens a file (Windows `GetOpenFileNameW`, other platforms fall back to a drop hint)
- Startup semantics (BUGS.md #3, merged with #2): the GUI front end `soarw.exe` and `--gui` started with no source show the empty main window (the “Open a file” poster) and do not print usage; the console `soar.exe` with no source still prints usage and exits 2; `--help/-h` prints usage and exits 0. With no explicit `--backend=`, the default backend is FFmpeg when it is compiled in (the old null default pretended to play any URI and showed a black screen — a file opened by a window session went silently black). File association: the Windows installer registers 18 extensions as “Open with → Soar” candidates (OpenWithProgids, does not take over the default, uninstalls without a trace); Linux uses `.desktop` with `Exec=soar --gui` + MimeType
- Status feedback: pause/buffering indicator, OSD toast, media-information overlay

Design and technology choices (the comparison and trade-offs between SDL2 custom drawing / ImGui / Qt / a web shell) are in [UI design](/ui-design).

## 2. v0.2 (fully landed)

- Playlist has landed: `soar <path> [more-paths...]` queues multiple positional arguments (the first plays immediately, the rest queue — mpv semantics; headless keeps the single-source contract); `N`/`Shift+N` go to the next/previous item (out of range only toasts, with no wrap-around), a natural end advances automatically (with Loop::Off it stops at the end of the queue as Ended, and Space replays); the `P` overlay lists the queue: clicking an entry plays it, `x` deletes it (deleting the current item only re-points the queue at a neighbour, without interrupting playback), the Loop button cycles off→all→one, and Shuffle randomizes; the model is `PlaylistStore` in ui_state.h (loop/shuffle/advance semantics have unit tests), and the window chain (enqueue/advance/auto-continuation/overlay) has X11 injection cases that verify the whole flow through both fixtures' media-info traces
- Screenshots have landed: the `S` key saves the most recently presented video frame as `screenshot.png` (FFmpeg's built-in PNG encoder, YUV420P→RGB24 conversion; on failure it only records `lastError` and toasts)
- Audio output device selection has landed (desktop): `IBackend` gains three methods — enumerate/query/switch endpoints (an empty string = system default); the FFmpeg backend enumerates devices through SDL2; the decode thread reopens on the new endpoint at the next audio frame (the old endpoint's queue drains naturally, so there is no abrupt cut; a switch made while paused takes effect on resume); the OSC audio-track menu lists “Output: default” plus the host's endpoints at the end; the choice is endpoint state rather than media state, so it is available before open and `close` does not reset it
- A-B loop has landed: the `L` key has three stages (set A → set B → clear); the decode thread jumps back at the boundary (including at EOF, i.e. an end-anchored loop); a manual seek disarms it (mpv semantics)
- Broader protocols have landed: HLS/DASH are smoke-tested against a local HTTP server (single-variant / master with two variants, VOD seek and playback progress, `SOAR_TEST_HLS_*`/`SOAR_TEST_DASH_AUDIO` fixtures); RTSP uses a minimal RTSP server embedded in the test (DESCRIBE/SETUP/PLAY + PCMA over RTP) for a live-stream smoke test; all three pass through FFmpeg demuxers with zero backend changes (known boundary: the `.sdp` file entry point is rejected by libavformat's default whitelist for nested rtp substreams; a direct `rtsp://` connection is unaffected)
- Subtitle experience has landed (basic): the subtitle-settings overlay (font-size slider, sync offset, visibility), `V` to show/hide, `[`/`]` to step the offset; the rendering and parsing pipeline is described in §1.3 and the subtitle batch notes
- Network-stream baseline: HTTP(S) sequential-playback smoke test, buffering-aware events (see §5 P0–P2)

## 3. v1.0 (a form closer to a “universal player”)

- Hardware decoding and the HDR colour chain (large cross-platform differences) **(the first hardware-decoding step landed 2026-10-10)**: `--hwdec=` (CLI) / `MediaSource::hwdec` — `none` (default, behaviour byte-identical to never passing the option), `auto` (tries the platform's usual order: Linux vaapi→vdpau, Windows d3d11va→dxva2, macOS videotoolbox), or an explicit device name (vaapi/vdpau/d3d11/dxva2/videotoolbox/cuda/nvdec). The wiring is all in the FFmpeg backend: setupDecoders confirms through `avcodec_get_hw_config` that the codec supports the hwaccel, then `av_hwdevice_ctx_create` attaches the device context (the codec and this instance each hold a reference, mirroring the two-reference shape of the hw_decode.c example), and the `get_format` callback reads this instance's negotiated format through `AVCodecContext::opaque` (per-instance, so concurrent opens cannot cross); decodeLoop downloads arriving hwaccel frames to YUV420P with `av_hwframe_transfer_data` before queueing them — the render/convert/display path is unchanged. Any link failing (the codec lacks the hwaccel, the device will not open, open2 refuses) silently falls back to full software decoding. Later opens within the window (playlist/dialog/drag-and-drop) reuse the session's `--hwdec` setting. On the CI side the test-only seam `SOAR_TEST_HWACCEL_ARM` (following the saveScreenshot `forceFailEncoder` precedent) drives the armed path: it negotiates stream-coded formats, aligns with the decoder's actual output format after open2, and runs the whole chain — get_format negotiation / frame download / teardown — on real libavcodec (docs/coverage-notes.md §3.21). **Boundary (honest)**: real hardware decoding is only observable on a real GPU — on GPU-less CI device creation always fails and the software fallback arm runs, so the `--hwdec=auto` case verifies “a clean fallback still plays”; the hardware frame path itself awaits a real-machine verification batch. **The first HDR→SDR wiring landed 2026-10-15**: `open()` recognises the HDR transfer characteristics on codecpar's `color_trc`, after correcting it with the decoder-context value — `AVCOL_TRC_SMPTE2084` (PQ) and `AVCOL_TRC_ARIB_STD_B67` (HLG) — sets `MediaInfo::hdr_video` and reports the status; the first frame lazily builds an avfilter graph (`zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p`) that converts every frame to SDR, and **if zscale is unavailable it selects PassThrough** — rather than convert, it does not produce a wrong picture. Measurement decided that only the zscale arm stays: the stock `tonemap` filter requires linear-light input, and without the EOTF step it tone-maps the **original HDR code values** (FFmpeg warns `Tonemapping works on linear light only`, and the same fixture measured a clearly low mean and a visibly wrong picture), so that fallback was deleted; the portability trap is that FFmpeg 8.0.1's buffer filter only accepts `colorspace`, and passing `color_primaries`/`color_range`/`color_trc` makes graph building return garbage instead of AVERROR and the whole chain fails silently, so the final graph carries zero colour parameters and relies on the frame's own labels passing through unchanged. **Boundary (honest)**: the PassThrough arm is reachable only in builds without libzimg (all CI legs have zscale — a cross-build fork rather than a gap), and HDR's **real-display and hardware colour-management side is untouched**; the test surface is docs/coverage-notes.md §3.26.
- Casting and remote control (**protocol decided 2026-10-11**: DLNA/UPnP AV first, soar acting as a control point driving a receiver MediaRenderer — a fully open standard with zero licensing risk, the largest installed base of receivers, self-implemented SSDP+SOAP with zero new dependencies, and “the receiver pulls the URL” is isomorphic with §5 P4's local HTTP bridge (LAN rebinding for the session only); Chromecast (CASTV2 URL-cast) is kept as a second-batch candidate, AirPlay is excluded (licensing/pairing encryption/reverse-engineering drift) and Miracast is excluded (screen mirroring is not media casting — wrong category). The comparison table and rationale are in the repository-root todo.md, “投屏协议选型”. **The control-point component landed (phase one, 2026-10-12)**: `src/cast/` — SSDP discovery (M-SEARCH/response parsing), device-description XML parsing (a relative controlURL resolved against the base URL per RFC3986), SOAP control (SetAVTransportURI/Play/Seek REL_TIME/Stop + fault pass-through), and GetPositionInfo polling (~1 Hz; GENA event subscription explicitly not done); `CastSession` strings together discovery → fetch description → rebind the bridge to the LAN interface (session window only, back to 127.0.0.1 on end/failure) → SetAVTransportURI → Play → poll. Receiver-side decoding: if the polled position never moves (beyond the grace window) it explicitly reports “the receiver cannot decode this container/codec, and this build has no sender-side transcoding”; repeated poll failures explicitly report “the renderer stopped answering”. Zero new third-party dependencies (plain sockets + hand-written XML/SOAP). **The product entry points are wired (phase two, 2026-10-12)**: the window's `t` key opens the casting overlay (phase rendering + position readout + Stop casting/Search again + clicking a discovered renderer row + toast; a one-shot SSDP burst with a re-entrancy guard, discovery on a background thread) and the CLI has `--cast=<descURL|auto>` (headless drives the session directly; window mode pre-arms and waits for the bridge to start Serving; auto does one 3s discovery burst and takes the first responder, or explicitly reports “No DLNA renderer answered”; a non-torrent source is refused before any socket is opened). **Control point completed (phase three, 2026-10-12)**: the pause action (SOAP `Pause` takes no arguments and resume reuses Play with speed 1 — the spec has no separate Resume; a successful Pause suspends the start grace window, and the grace test excludes paused time), GENA event subscription (SUBSCRIBE (CALLBACK/NT/TIMEOUT) → SID renewal → UNSUBSCRIBE, with the event callback an HTTP endpoint contained within the session; NOTIFY LastChange→TransportState coexists with polling, events first — events are only liveness evidence for the polling bypass, they do not take over the state machine), and sender-side transcoding (with FFmpeg present: bridge source demux → decode → re-encode to H.264/AAC (an MPEG-TS-compatible pair that is copied as-is without the decoder) → MPEG-TS → a session-contained HTTP endpoint, `--cast-transcode` / an overlay toggle; the endpoint is a live point — Seek is explicitly refused (there is no seekable on-disk artifact), only one pull stream is served at a time (a second gets 503), and a slow pull is back-pressured through the queue limit all the way back to the bridge read; the transcoding session's DIDL `<res>` is annotated `protocolInfo="http-get:*:video/mpeg:*"`, and the error text for a receiver that cannot decode forks on the transcode switch: with transcoding off it suggests `--cast-transcode`, and if it still stalls with transcoding on it honestly reports “still stalling on the transcoded stream”).**SSDP interop axes hardened (2026-10-24 — the four axes the real-device matrix names)**: the M-SEARCH window now sends three bursts 300 ms apart instead of two (flaky stacks ignore the first, or it lands before they are ready to answer), and rides `IP_MULTICAST_TTL 2` — TTL 1 dies at the first router, and a receiver often sits behind it on another segment (a guest VLAN, a bridged subnet); `--cast-iface=<ip>` pins the burst's multicast interface for machines with two LAN faces (a VPN beside the house LAN), where the system's multicast route picks the wrong one; reply parsing accepts the search-target forms receivers echo back instead of the asked service target (`uuid::`, `upnp:rootdevice`, the device type), bare-LF line endings, HTTP/1.0 status lines, a body after the blank line, and repeated header lines (the first occurrence wins). The fixture's M-SEARCH answerer is now shaped per case (a delayed answer inside its MX, LF endings, the three ST forms, the header lines some stacks omit, a description hosted off 127.0.0.1) and each shape is discovered end to end on loopback — the local legs of MX 延迟/应答形态/组播路由/跨子网. **Boundary (honest)**: the routed leg of the TTL and the real manufacturer answer shapes still need a real device; a burst pinned to loopback does not reach a responder that joined the group on the default route (the CLI fixture answers that way) — exactly the mismatch `--cast-iface` exists to fix. **Windows entry (BUGS.md #3)**: `--open-dialog` summons the open-file dialog right after the first frame, the same picker as the O key but without needing the foreground focus an automation session cannot grant; without a file dialog in the build it degrades to the toast the O key already gives.
**Boundary (honest)**: control point only — no renderer/DMS role; on builds without the FFmpeg backend `--cast-transcode` fails explicitly (it reports that the build lacks the backend rather than silently casting directly); end-to-end against a real SSDP responder (the real-device matrix) is unverified — product-side discovery is verified through the “no answer” branch, and the discovery→SOAP→transcode real chain is covered by component-level cases (an embedded minimal MediaRenderer + a real self-seeded torrent + a real small media fixture, the whole chain). Test surface: pure-logic unit tests + an in-process minimal MediaRenderer smoke test (following the P2 embedded-RTSP precedent), see `tests/test_cast.cpp`; product-side wiring cases (headless fake-renderer full handshake + a six-shot X11 walkthrough) are in `tests/test_cli.cpp`)
- Media library and scraping, history/sync, multi-device consistency (**the basic library layer landed 2026-10-10**: local media library `src/app/ui/library.{h,cpp}` — watched-folder scanning (recursive, mtime token, pruning of vanished files, non-watched paths untouched), line-based storage (`library.txt` under XDG_STATE_HOME/APPDATA), playback history (position/count/timestamp; ## 5. Watch while downloading (the network playback roadmap)

The target shape references “Xunlei Kankan”: given a network source it starts playing immediately, data lands on disk in the background during playback, seek and re-watch go through the local cache, and a dropped network/stream can recover. The FFmpeg backend feeds a URL straight to `avformat_open_input(url)`, so HTTP(S) sequential playback is essentially already watch-while-downloading (a socket stream read); the real gap is closed in stages:

| Stage | Content | Size |
|---|---|---|
| **P0 baseline smoke** | Verify the status quo: a local HTTP service + `--backend=ffmpeg http://...` sequential playback, Range seek, disconnect behaviour; fix the pitfalls found | Small |
| **P1 buffering awareness** | Add `BufferingStarted`/`BufferingEnded` events to the core event model (without touching the state machine); the AVIO interrupt callback acts as a network-stall watchdog: a read stall over 10s reports buffering, and only past a 60s tolerance does it abort into Error (it does not actively disconnect — a slow source heals itself on the same connection); proven by slow-HTTP fixture cases | Done |
| **P2 adaptive protocols** | HLS/DASH/RTSP are natively supported by FFmpeg demuxers and pass through with zero backend changes (no `protocol_whitelist` is set, so everything is allowed by default); fixtures: AAC-passthrough single-variant / master-with-two-variants / MPD / an embedded python RTSP-RTP server (PCMA over UDP); cases: HTTP smoke ×3 + VOD seek against a Range-capable server (seekable=true, synchronous seek while Stopped, playback progress) + an RTSP live-stream smoke test (incidental fixes: a negative duration on a live stream is clamped to 0, and a stream without a duration refuses seek to prevent clamp UB) | Done |
| **P3 download-while-storing** | A custom AVIO layer: download to a local cache on disk, play from the cache, issue Range requests for not-yet-downloaded segments, resume from a partial cache, and show download progress in the UI. **P3a minimal core**: a standalone `HttpCache` component (two files `<fnv1a64(url)>.meta/.data`, a bitmap of 1 bit per 256 KiB block, meta records the plaintext url and rebuilds on mismatch, data is a sparse `ftruncate`; a built-in minimal http-only client with a 60s `SO_RCVTIMEO` backstop) + a thin FFmpeg avio adapter (a seek callback including AVSEEK_SIZE; `AVFMT_FLAG_CUSTOM_IO`) + the CLI `--cache-dir=`; the same URL replays offline (integration case: play to the end, kill the server, reopen and make progress); https passes through without caching in this batch. **P3b seek hole-filling/resume**: integration cases pin down three contracts — a seek from the stopped state into an uncached region fetches only the target block (a bitmap assertion shows the span from the head to the target is still holes and `cachedBytes<size`), reopening offline with a partial cache after killing the server resumes inside the cached range with zero bitmap growth, and offline playback running into a hole reports an Error event rather than hanging (avio miss→EIO→fatal). **P3c download-progress events**: the cache avio read callback emits `DownloadProgress` during playback, throttled to 1/16 steps of the source size (the first read only calibrates; a fully cached offline playback emits zero events; the payload uses `Event::message`'s `"downloaded/total"` format, and the Event-member freeze policy is in coverage-notes §3.8); the CLI prints it and the window shows a Downloading badge, and an Xvfb windowed case asserts the event sequence is monotonic and terminates at 100%. | **P4 P2P** | libtorrent (BSD, no compliance conflict) for piece-ordered download; or a local HTTP proxy bridge (the BT stream is disguised as `http://localhost:port/`, with zero FFmpeg backend changes). **Decision (2026-10-01): go with the local HTTP proxy bridge** — libtorrent serves only as the download core (vendored at a pinned version, see `third_party/libtorrent/VENDOR.md`), and the `TorrentStream` component presents the selected file at `http://127.0.0.1:<port>/` with Range support; the playback chain reuses the existing http entry point, with zero changes to `IBackend`/the FFmpeg backend, matching the “core abstraction stays put” architecture convention; the bridge component lives in `src/p2p/` (inside the coverage gate with `soar_p2p_tests` since 2026-10-05). **P4a minimal core**: vendored libtorrent 2.0.15 (prune + one `add_subdirectory(bindings)` guard, Boost headers only; `encryption=OFF` uses the bundled SHA-1/256 and has zero OpenSSL dependency — a peer forcing MSE encryption in a real swarm cannot connect, a P4b boundary) + `TorrentStream` (`src/p2p/`, libtorrent headers kept out of public interfaces): a 127.0.0.1-only HTTP service (random port, the three Range forms 206/416, keep-alive, 256 KiB chunked streaming) + sequential download + fetch-on-demand (a missing piece before a read triggers `set_piece_deadline` + 25ms polling, and a 60s timeout breaks the connection so FFmpeg sees an ordinary read error); a CLI `.torrent` positional argument plays immediately (`--torrent-store=`/`--torrent-peer=` host:port repeatable/`--torrent-index=`), and magnet is explicitly refused and left to P4b; walkthrough (a real two-session swarm, `tools/seed_torrent` seeding/rate-limiting): a 26MB mp4 at a 1.2MB/s cap plays and downloads in parallel, RIGHT forward-jump and HOME re-watch mid-download (after killing the seeder, purely local continuation for 7s+), reopening the same store with no seeder verifies 12.2MiB of resume, and ESC exits cleanly; ## 6. Subtitle services (download and AI translation)

Dependency order: land v0.2's subtitle rendering foundation (font/size/offset) first, then connect external subtitle sources.

- **Embedded ASS/SSA style rendering**: an embedded ASS/SSA track is no longer downsampled to plain text — style/font/colour/positioning are rendered through **libass** (the open-source ASS rendering library that ships alongside FFmpeg; apt `libass-dev` on Linux, the vcpkg `libass` port on mac/win). **The boundary between dependencies and our own code**: the rendering itself is entirely libass's capability; what this repository writes is the wiring and compositing — the `AssRenderer` thin wrapper component (libass headers stay out of public headers; libass's glyph bitmaps are composited into one RGBA canvas with straight-alpha src-over, and the `changed` semantics make the texture upload only when the picture changes; an internal mutex lets the decode thread feeding events and the UI thread rendering share one instance, and a build without libass where `available()=false` automatically falls back to the existing plain-text path, the same optional-capability-degradation contract as SDL2/FFmpeg/ImGui); the FFmpeg backend registers Matroska attachment fonts (`ass_add_font`) on open, feeds CodecPrivate (script header + styles) to the streaming track, and reassembles libavcodec's ASS payload back into the complete `Dialogue:` lines libass wants — libavcodec's ass decoder produces the 8-comma `ff_ass_get_dialog` form (no `Dialogue:` prefix, no start/end times, with the duration carried on Matroska BlockDuration / the packet duration), and reassembling the full 10-field line from “rect fields + packet pts/duration” is the key wiring step; the UI blends the canvas texture directly after the video letterbox (the bare-window path without ImGui works the same way). Font resolution is pinned to `ASS_FONTPROVIDER_NONE` + container attachment fonts: no fontconfig, no system font enumeration, so rendering is deterministic and testable — test fixtures use the Noto Mono bundled in the repository (SIL OFL 1.1, `tests/fixtures/FONT-LICENSE.txt`) and assert pixel by pixel that “every visible pixel is exactly the pure red the script declares”. On a backward seek `ass_flush_events` clears events, preventing duplicates from the decoder rescanning. Style rendering follows the selected embedded ASS/SSA track — the default track picked at open is fed in at open time, and switching to a non-default ASS track rebuilds the streaming track from that track's own CodecPrivate (the embedded-track-selection semantics batch, see the known-boundary section below); an embedded text track that is not selected still goes through the original plain-text queue (external SRT/WebVTT goes through the canvas in libass builds from batch 1c on, see below).
- **External .ass/.ssa document subtitles (batch 1b)**: an external ASS/SSA sidecar becomes a first-class subtitle track, sharing the same `AssRenderer` as embedded ASS (the rendering capability is as above, still libass's; what this batch writes is the redirection wiring for “the renderer follows the last selected ASS source”). **Load chain**: sidecar candidates use the `.ass`/`.ssa` extensions (enumeration + case-insensitive extension + content probing for `[Script Info]`/`Dialogue:`, without misreading SRT/VTT cue text that quotes "Dialogue:"), the HTTP retrieval protocol's extension field accepts `ass`/`ssa` too, and `storeExternalSubtitle` writes the `.ass` suffix; for an ASS document `loadExternalSubtitle` first runs an `assDocumentCues` extraction as the load gate (a file with not one usable Dialogue is not a subtitle), and with libass present it `loadDocument`s the whole document (faithful styles; a build without libass degrades it to a plain-text track — the extraction is the track, with `{\...}` override blocks stripped, `\N`/`\n`→newline, `\h`→space, and a 2s default display duration when end≤begin, with the same fault tolerance as the SRT parser). **Redirection semantics**: selecting a document track → close the embedded streaming feed and load the whole document (the canvas then follows the playback head); selecting an embedded ASS track again → rebuild the streaming track from the CodecPrivate stashed at open (events continue streaming from the decoder's current position, with **no automatic rescan**: the boundary this batch does not close is that cues before the re-selection point only show after the next backward seek rescans); selecting an embedded text track or `disableSubtitles` → swap in an empty track and clear the canvas (from batch 1c on, selecting an external text track also goes through the document path, see the next item). While a document is active the decode thread discards embedded stream events (preventing a plain-text echo layered onto the canvas), and both direction flags are atomic (written by the UI thread, read by the decode thread, layered with the renderer's own mutex). **UI font**: an external document has no container attachment fonts, so runWindow sets the renderer's default font from the same candidate list as the UI font (best-effort — a document whose font resolves from registered fonts/attachments still renders as usual). Tests: `assDocumentCues` unit tests (timestamp widths, text transforms, bad-line tolerance, CRLF), sidecar/HTTP candidate/storage-extension cases, and three media-suite cases — a pixel-green assertion for an external document (one path per build: libass canvas vs plain-text pump), a red assertion for restoring the embedded stream, and a canvas-release assertion for disable.
- **Subtitle download**: search public sources such as OpenSubtitles by media hash/file name, download, and align with the track; built as a pluggable `SubtitleProvider` interface (the core defines the interface, implementations can swap sources), failing silently into “no subtitles”. **The interface, the local sidecar implementation and the playback wiring have landed**: `SubtitleProvider` has only two methods, `findCandidates` (list candidates) and `fetch` (get the text), and `SidecarSubtitleProvider` looks for same-named `.srt`/`.vtt` next to the media (supporting language/forced tags such as `movie.en.srt` and `movie.en.forced.srt`, case-insensitively); the SRT and WebVTT text parsing is a dependency-free pure function whose tolerance is documented in the header comment (BOM, CRLF/bare CR, a missing hours field, 1–6 decimal places, WebVTT's NOTE/STYLE/header blocks, skipping bad blocks and continuing, and so on). `IBackend::loadExternalSubtitle(path, out_id)` attaches a sidecar as a real subtitle track: the external track id counts from the container's stream count (`nb_streams + slot`) so it cannot collide with an embedded track, the track name is the file name, and the codec is judged from content as `subrip`/`webvtt`; `selectTrack` is relaxed accordingly to accept that id. A sidecar has no decode thread, so frames are pumped by the playback head inside `tryGetSubtitleFrame` into **the same queue as embedded subtitles** (UI rendering is unchanged and cannot tell the two sources apart): when the playback head goes backward (seek / A-B wrap / replay) the cursor rescans from the start, and when it jumps far forward only the last 4 cues are queued. A load failure (no media / unreadable / no cues) only records `lastError` and emits no Error event — a missing sidecar is normal and the media keeps playing. On the UI side the subtitle menu and the Subtitle Settings overlay list the candidates (the directory is enumerated only while the menu is open; there is no file dialog), and selecting one loads and selects it. **The search/download source has landed (a pluggable HTTP client with a custom line protocol; it does not claim compatibility with OpenSubtitles or any existing service API)**: `ExternalSubtitleProvider` talks to a **documented minimal line protocol** through a self-contained small blocking HTTP client — search is `GET {endpoint}?size={bytes}&hash={16 hex}&name={main file name}` (the key goes in an `X-API-Key` header), a 200 response carries one candidate per line with TAB-separated url/language/title/extension and `#` for comments, and only `http://` candidates are accepted (TLS is explicitly out of scope, as with http_cache); download is `GET {candidate url}`, and the body must be recognised by the core parser as SubRip/WebVTT to count as success (a 200 HTML error page does not become a subtitle track). The hash is “the sum of the u64 little-endian words of the first and last 64 KiB + the file size” (`mediaHashHex`, recomputable independently by the server). The contract is unchanged: endpoint and key are always injected as configuration — the window reads them from the environment variables `SOAR_SUBTITLE_ENDPOINT` / `SOAR_SUBTITLE_API_KEY` / `SOAR_SUBTITLE_TIMEOUT_MS`, and with nothing configured it always returns no candidates and makes zero network requests, with the key never entering the repository or the logs. The UI subtitle menu appends a `[download]` section after the sidecar candidates (searched once per uri and cached; anything already downloaded in this session is not listed again), and selecting one downloads it → stores it in the system temp directory's `subtitles/` (`storeExternalSubtitle`, with the title sanitised against path traversal) → goes through the same load pipeline as a sidecar, and a failure only toasts "Download failed". Every failure branch (unconfigured, unreachable, timed out, non-2xx HTTP, unparseable response, unreadable media) degrades silently into no candidates/false per the interface contract, and the media keeps playing. All tests hit a local fixture HTTP server (`test_http_servers.h`'s catalog/empty/500/404/slow-answer/bad-key modes + a raw-bytes garbage socket) and never touch the real internet.
- **Subtitle text translation**: when a subtitle track/file exists, send its text to an LLM/translation API in batches and produce a translated subtitle track (the lightweight path). **Both the core path and the window wiring have landed (`SubtitleTranslator` + the subtitle menu's `[translate]` row, fully offline in tests)**: given SubRip/WebVTT text, cue text is folded to one line and split into blocks of `batch_cues` (default 16), then POSTed as numbered lines (`1. text`) to the user-configured OpenAI-compatible endpoint `{endpoint}/chat/completions` (the minimal common subset of three fields — `model`/`temperature:0`/`messages` — with the key in `Authorization: Bearer`; only `http://` is supported, TLS being explicitly out of scope as with http_cache); the response must give translations **numbered line by line and matching the batch's line count**, and a missing line, a lost number, a non-2xx, a timeout, unreachability, or no configuration (empty endpoint or model) all mean false with a reason — **all or nothing**, so a half-translated subtitle track is never produced. The output mirrors the input format (srt→srt, vtt→vtt) with the timeline and cue numbers preserved, and after `storeExternalSubtitle` → `loadExternalSubtitle` it becomes a real subtitle track. JSON escaping in the response's `choices[0].message.content` (including `\uXXXX` and surrogate pairs, with a lone surrogate becoming U+FFFD) is handled by a minimal hand-written decoder with no JSON library. **Window wiring**: the subtitle menu and the Subtitle Settings overlay append `[translate] <track name> -> <language>` rows after the `[download]` section — first the external tracks this window itself loaded (the window remembers the source path; ASS/SSA documents and TTML/DFXP files are not translator inputs, since the batch path only speaks numbered SubRip/WebVTT cues and those two produce no rendered lines), then the embedded text tracks (**the “export embedded tracks first” slice has landed**). Embedded rows are filtered by a codec whitelist (`subrip/srt/ass/ssa/movtext/mov_text/webvtt/text` — the names are what `avcodec_find_decoder(cid)->name` actually reports; mkv subrip reports "srt" and mp4 mov_text reports "mov_text" with an underscore, and the whitelist accepts both; bitmap subtitles pgssub/dvdsub and obscure codecs get no row, and exporting them could only fail). Clicking an external row reads the file → batch-translates → saves → goes through the same load pipeline as a sidecar; clicking an embedded row first runs `exportSubtitleText` to demux that subtitle stream into plain SubRip and then goes through the same translation tail — the export **reopens the input source independently** (a plain `avformat_open_input`, not touching the playing decode path or the avio cache), with the snapshot taken under the decode mutex and the demux outside the lock, executed synchronously on the UI thread (local/loopback sources are millisecond-scale, and a slow endpoint is bounded by the timeout); each track is translated once per session (external tracks keyed by title, embedded tracks by track id — container titles are often duplicated, so the row id gets a `##tr<track id>` suffix purely for ImGui de-duplication, without changing what is displayed); both kinds of failure only toast "Translation failed" and leave the original track untouched (an export failure likewise only toasts, with no Error event). The embedded-row chain is proven by a real walkthrough (Xvfb windowed + a local stub endpoint, seven legs: subrip mkv / mov_text mp4 / ass with overrides stripped on export, once per session, fail500 and a short answer with missing lines both refused, and no configured endpoint means zero rows). The contract matches the download source: endpoint/key/model/target language are all injected through environment variables (`SOAR_TRANSLATE_ENDPOINT` / `SOAR_TRANSLATE_API_KEY` / `SOAR_TRANSLATE_MODEL` / `SOAR_TRANSLATE_TIMEOUT_MS` / `SOAR_TRANSLATE_LANGUAGE`, with the target language defaulting to "English" and no language selector in the window itself — one language is enough for an entry slice), and with endpoint or model unconfigured it renders no translation rows at all and makes zero network requests, with the key never entering the repository or the logs. The request shape and the end-to-end chain (menu selection → downloaded track → translated track with an incrementing id) are asserted field by field against a local fixture chat server (`test_http_servers.h`'s chat mode + `requests.log` request recording + an Xvfb windowed injection case), and the real internet is never touched.
- **Real-time speech translation**: media without a subtitle track goes through ASR (a local whisper-class model or a cloud service) + translation + subtitle rendering (the heavyweight path, placed last).
- **External SRT/WebVTT through libass default styles (batch 1c)**: in builds with libass, selecting an external SRT/WebVTT track no longer goes through UI text drawing — at load time `loadExternalSubtitle` synthesises the track's cues into an ASS document with default styles (the pure function `synthesizeAssDocument`: white text with a black outline, bottom-centre, a font size scaled with the video height (288p gets the classic 20px, 1080p gets 77px), PlayRes following the video and falling back to ASS's own 384×288 when the video size is unknown; cue text is preserved byte for byte except newline→`\N`), going through the same `loadDocument` canvas path as batch 1b. **Dependency/own-code boundary**: glyph rendering is libass's, the default styles and the synthesis are this repository's; builds without libass change by zero (the plain-text pump stays as it was). **Three things converge along with it**: ① the canvas's `renderAt` now takes “playback head + subtitle sync offset”, and the V visibility toggle applies to both the canvas and UI text — batches 1a/1b's canvas previously ignored both (a regression risk for text tracks moved onto the canvas, closed here, benefiting embedded ASS and .ass documents equally); ② selecting an external text track means document mode: the decode thread discards embedded ASS events, and the UI's plain-text drawing is skipped entirely while a document is active (the backend gains a `subtitleDocumentActive()` query; the anti-double-draw gate sits in the UI rather than the pump — the pump's own semantics are the same in both builds, since tests pulling frames drive it as usual and the only frame-pull point in production is this gate, so a closed gate stops the pump and the observable behaviour is identical to bypassing it, the difference being only that the code path is not split by build) — **batch 1b's leftover “text sidecar × embedded ASS stream overlay” is hereby closed in libass builds**, and embedded text frames in the queue are likewise not shown while a document is active (builds without libass still overlay, see below); ③ `disableSubtitles` and the release semantics for selecting an embedded track again reuse batch 1b. **Boundary (honest)**: an embedded text track's (mov_text/subrip stream) cues are produced streaming by the decode thread rather than all being in hand at load time, so they do not go through load-time synthesis — from the embedded-track-selection semantics batch on, they reach the canvas **when selected** through the same synthesised default-style header (a zero-cue document as the header + Dialogue events reassembled per frame, see the known-boundary section above); the UI font-size slider does not affect canvas-rendered tracks (styles belong to the script/default styles, the same contract as .ass documents), and the sync offset acts at render time (`renderAt(pos+offset)`), so re-synthesising is unnecessary. Tests: `synthesizeAssDocument` unit tests (script shape, PlayRes fallback, font-size band, inverted end default duration, a round-trip oracle through `assDocumentCues`); media suite — the sidecar playback case asserts the same in both builds (the pump emits frames as usual, with timing from the file; in a libass build that queue output is the same text as the canvas — the anti-double-draw gate is in the UI, not the pump), plus a new “a text sidecar takes over the embedded ASS canvas” case (red baseline → select SRT → the canvas is non-red with glyphs); the assdrive X11 case adds a V-key round trip (gating both arms of canvas visibility).

Known boundary (the state after the embedded-track-selection semantics batch closed): an embedded track's “selection” is **decode semantics**, no longer metadata — the decode thread only processes the selected subtitle stream (or the open default that was not cancelled). The default track at open is still decoded into the plain-text queue as before (the existing “subtitles on open” behaviour and test contract are unchanged); when an embedded track is explicitly selected and it is not the default track for which the decoder was created at open, a runtime subtitle-decoder switch is performed first (the same pending-handoff contract as audio-track switching; on failure the selection fails and the original track keeps playing), and in a libass build that track's cues are fed to the canvas — an ASS/SSA track re-attaches the streaming track with its own CodecPrivate (not relying on the stash from open), and a text track (mov_text/subrip stream) attaches a synthesised default-style header (`synthesizeAssDocument` zero-cue document, the same styles as batch 1c: white text with a black outline, bottom-centre, a font size following the video height), and when the decoder emits a bare `SUBTITLE_TEXT` rect it reassembles one Dialogue event per frame (the pure function `assDialogueLineFromText`, newline→`\N`, other bytes preserved; which rect shape the decoder gives varies by version — measured on FFmpeg 8, mov_text emits ASS rects and takes the byte-feed arm, while the reassembly arm serves shapes that emit bare text); selecting a sidecar or `disableSubtitles` closes the decode gate and clears the subtitle queue, and the embedded stream produces no more frames — **the overlay surface left over from batches 1b/1c (including a text sidecar and an embedded subtitle stream interleaving in one queue in builds without libass) is hereby closed in both builds**. Boundaries still honestly recorded: after a selection/switch, events continue streaming from the decoder's read position, so cues before the selection point only show after one backward seek rescans (the batch 1b boundary, unchanged); the UI font-size slider does not affect canvas-rendered tracks — once an embedded text track is selected it is a canvas track, the same contract as external documents and text tracks.

Architecture convention: translation/ASR services go through **user-configured OpenAI-compatible endpoints** (base URL + key); the core embeds no cloud-vendor credentials and does not force networking; all AI capabilities are optional plug-in services, and offline scenarios are unchanged as before.
